# Cleaned dataset: AIDev-pop Python v1

This is the 100-PR dataset used for defect detection and executable testing. It
grows the 5-PR pilot in [`../pilot/`](../pilot/) by applying the same metadata
filters and adding text cleaning, GitHub screening and a repository-grouped split.
For the counts, see [`STATS.md`](STATS.md).

Source: AIDev v2, [Zenodo record 16919051](https://zenodo.org/records/16919051), AIDev-pop subset
(Li, Zhang and Hassan, 2025).

## Files

| File | Contents | Give to the review agent? |
|---|---|---|
| `prs.jsonl` | One cleaned PR per line (fields below). | Yes (the input). |
| `review_evidence.jsonl` | Historical human and bot reviews and inline comments for each PR. | **No.** This is held-out evaluation evidence only. |
| `exclusions.jsonl` | PRs screened against GitHub and rejected, with the reason. | n/a |
| `build_info.json` | Build parameters and the selection funnel. | n/a |
| `stats.json`, `STATS.md` | Dataset statistics, generated by the stats script. | n/a |

Raw diffs and GitHub API responses are cached locally and are **not committed**, following the
pilot's choice not to redistribute patches. `diff_sha256` lets you check that a re-fetched diff
matches the one we used.

## How PRs were selected

1. **Join** `pull_request`, `repository`, `related_issue` and `issue`.
2. **Metadata filters:**
   - the repository's primary language is Python and it has more than 100 stars;
   - the repository name and PR number are valid, and the PR is not a duplicate;
   - the title is not documentation-only (`docs:`, `doc(`, `documentation ...`);
   - the title, cleaned description and linked issues together have at least 10 words.
3. **Ordering:** pilot PRs come first. The remaining repositories are shuffled with seed 572, and one
   random PR is drawn from each, so every PR comes from a different repository.
4. **GitHub screening**, in that order, until 100 PRs pass. A PR is excluded if:
   - its PR, file list or diff is unavailable;
   - it has no added or modified `.py`/`.pyi` file;
   - it has more than 1,000 changed lines or more than 30 files. This size cap keeps PRs
     reviewable in the human study and testable in reasonable time.
5. **Split:** a repository-grouped 80/20 split, with no repository in both splits. Pilot PRs keep
   their pilot split. The remaining evaluation slots go to the repositories that sort first by
   `sha256(seed:repo)`, so adding PRs later does not reshuffle earlier ones.

Four of the five pilot PRs are included. `GetSoloTech/solo-server#45` was dropped because it
changes 2,711 lines, which is over the size cap.

## Text cleaning

Agent PR bodies mix requirement text with platform boilerplate. `dataset/clean.py`:

- normalises line endings and whitespace;
- removes HTML comments (mostly PR templates), the Copilot tips banner, Ellipsis summaries and
  mermaid diagrams (Devin);
- removes boilerplate lines: Codex task links, Devin run links and "Requested by" lines, Copilot
  "Thanks for assigning" text, Claude Code "Generated with" footers and `Co-authored-by` lines,
  and Cursor background-agent links;
- moves the agent's own **Testing** section (for example Codex's `## Testing` list) into
  `agent_reported_testing`, and sets `agent_reported_test_failure` when that section reports a
  failing command. These are the agent's claims, not ground truth.

`cleaning_rules_applied` lists the rules that fired for each PR. The raw text is still available in
AIDev under `pr_id`.

## Fields in `prs.jsonl`

| Field | Meaning |
|---|---|
| `pr_id`, `repository`, `pr_number`, `pr_url`, `patch_url` | Identity and links. |
| `agent` | OpenAI_Codex, Copilot, Devin, Claude_Code or Cursor. |
| `pr_state` | `merged`, `closed` (not merged) or `open`, as of the AIDev snapshot. |
| `created_at`, `closed_at`, `merged_at` | Timestamps from AIDev. |
| `repository_stars`, `repository_license` | From AIDev. |
| `title`, `pr_description` | The cleaned title and description. |
| `linked_issues` | `[{number, title, body, state, html_url}]`, with bodies cleaned. |
| `requirement_text` | The title, description and linked issues as one Markdown text: **the requirement**. |
| `requirement_words` | Word count used by the filter. |
| `agent_reported_testing`, `agent_reported_test_failure` | The agent's self-reported testing. |
| `cleaning_rules_applied` | The cleaning rules that changed this PR. |
| `base_ref`, `base_sha`, `head_sha`, `merge_commit_sha` | Commits from GitHub at build time. The head is frozen here. |
| `n_commits`, `additions`, `deletions`, `changed_lines`, `n_changed_files` | Size of the change. |
| `changed_files` | `[{path, status, additions, deletions, previous_path}]` |
| `changed_python_files`, `changed_test_files` | Python files the PR adds or modifies, and the subset that are tests. |
| `diff_sha256` | Hash of the GitHub `.diff` used. |
| `split` | `development` or `evaluation`. |
| `in_pilot` | Whether the PR came from the pilot. |

## Known limitations

- **Sample:** one PR per repository from 100 of 493 eligible repositories. Codex dominates
  (57 PRs), as it does in AIDev-pop; Claude Code and Cursor have only 6 and 4.
- **Review evidence is thin:** 25 PRs have a human review, and 10 have human inline comments. Use it
  as a secondary, noisy signal, as the proposal says.
- **Live data:** heads, and open PRs (15), can change after the build. Use the frozen `head_sha`.
- **Requirement quality:** at least 10 words is a weak bar. Several Codex PRs are one-line
  summaries. Requirement specificity has not yet been labelled by hand.
- One PR reports 1,946 commits for a small diff. This is a branch-history artifact; its diff is
  normal.

## Rebuild

```bash
pip install -e ".[data,analysis,dev]"
# Download pull_request, repository, related_issue, issue, pr_reviews and pr_review_comments
# (.parquet) from the Zenodo record into RAW/.
export GITHUB_TOKEN=...            # e.g. $(gh auth token); about 3 API calls per screened PR
agent-code-reviewer dataset build --raw RAW --cache CACHE --out data/clean --target 100
agent-code-reviewer dataset stats --data data/clean
```

The GitHub responses are cached in `CACHE`, so a rebuild with the same cache is deterministic.
